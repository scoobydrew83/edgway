## What "Kong-compatible" covers

The Kong-compatible Admin API serves Kong 3.9's entities and plugin schemas, so decK and Kong's Terraform provider work against it unchanged. It runs on the admin Worker's root and under `/default/` for workspace-prefixed clients. Kong's own clients are tested against it in CI: decK `sync`, `diff`, `dump` and `gateway validate`, the online validation that calls `/schemas/{entity}/validate` (including a corpus of Kong's own sample files), and Terraform `init`, `plan` and `apply` of the example module.

Each first-party plugin implements its Kong namesake's configuration. Enterprise-named plugins (`openid-connect`, `ai-rate-limiting-advanced`) are independent implementations of that configuration, not Kong's code. [Migrating from Kong](/guides/migrate-from-kong) lists where behaviour differs, for example hashed key-auth keys and vault-only jwt secrets.

## Runs differently

- **least-connections runs as round-robin on Workers.** A gateway isolate doesn't see other isolates' open connections, so Edgway accepts `least-connections`, and Kong's `latency`, and balances them round-robin. They are never silent:
  - every publish lists such upstreams under `warnings`, which the admin UI and `edgway publish` show;
  - the gateway logs `gateway.upstream_algorithm_fallback` once per published config.
- **key-sets and keys** are always empty and can't be written. Kong uses them for Enterprise plugins (jwt-signer, openid-connect's JWKs), not for the OSS jwt plugin, which verifies with jwt credentials as in Edgway. decK dumps none. A decK file with `key_sets` or `keys` fails to sync, naming the entity (404 from `/key-sets`). decK's `gateway validate` skips them.

## Not supported yet

These Kong features are not in this release:

- active health checks; passive health checks work;
- mTLS, certificates and SNI on the data plane;
- a cache purge API;
- Cloudflare's Rate Limiting binding for `policy: local`. Every rate-limiting policy counts exactly in a Durable Object instead.

A configuration that uses something Edgway can't run is refused at publish, with the reason, rather than ignored. For example, routes matched by `sources`, `destinations`, `snis` or an `expression` are refused.
